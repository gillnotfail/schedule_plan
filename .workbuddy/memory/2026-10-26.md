## 第 27 轮：专注准备态压成一屏 + 修滚轮手感

用户："专注模式这里有个问题，就是现在比一页还长…备注太多了…时间选择也很卡顿，上下滑动也很慢。"

**两个真 bug 和一个布局问题**：

1. **滚轮"滚一格就被拽停"**（这才是"很慢"的根因）：`FocusDurationWheel` 滚一格 → `_emit` 上报 →
   页面 `setState` → 新值经 `widget.value` 回灌 → `didUpdateWidget` 里 `jumpToItem` 三列 →
   **正在进行的惯性滚动被当场打断**。加 `_lastEmittedSeconds` 拦回音：等于自己刚上报的值就
   只同步字段、绝不动 controller。这是"同一份数据既是输入又是输出"的经典坑。
2. **每格都 `AppMotion.select()`**：连续滑动时震动串成一片、主线程 haptic 排满，手感发涩。
   改成 `NotificationListener<ScrollEndNotification>`（`depth == 0` 且非程序化）才震一次。
3. **准备态超一屏**：删预览环（170px，数字与滚轮完全重复）、预设改单行横滑（原来 11 个
   占四行）、两个开关并一排、"更强锁定"说明改成开启后才出现。

新增 `AppConstants.focusWheelItemExtent = 40`（不复用设置页 44：格小滚得快，40×4=160 才塞得下）。
新增回归测试：411×850 窗口断言 `ListView.maxScrollExtent == 0`。

## 第 28 轮：修「完成专注后 App 退不出去」

用户报：完成专注后回到 App 页面就退不出去了，怀疑锁屏延续到了完成后。

**确认，是真 bug，根因比"忘了解锁"隐蔽**：`_releaseLock()` 里写的是
`if (_screenLocked) { ... exitLockTask(); }` —— 靠"我记得锁过"决定要不要解。但首次进入
「屏幕固定」时系统会弹确认框，`startLockTask()` 之后**立刻**读 `lockTaskModeState` 仍是 NONE，
于是 `enterLockTask` 报 false、`_screenLocked` 记成 false。用户一点确认就真锁上了，
释放时被那个 `if` 跳过 → 整个 App 被系统钉死。

**顺带发现一个更脆的设计**：`_applyLock` / `_releaseLock` 都是顺序 `await` 三件事。写诊断探针时
量到 **`SystemChrome.setEnabledSystemUIMode` 在 widget test 里永远不返回**（`chromeDone = false`），
后面的 `setKeepScreenOn` / `enterLockTask` 根本排不上队。同样的结构在真机上只要任何一步卡住，
`stopLockTask()` 就永远执行不到 —— 死法一样。

**改法**：
1. `enterLockTask` 回三态（0 拿不到 / 1 已锁 / 2 待确认），`pending` 不再当失败；
2. `_releaseLock()` **无条件**调 `exitLockTask()`，删掉 `_screenLocked` 字段 ——
   释放不问理由，原生侧本来就是幂等的；
3. 释放的三件事：前两个 `unawaited`，只 `await` 最后那个 `exitLockTask`；
4. 原生 `exitLockTask()` 返回"是否确认已解除"：读完仍锁定就 `postDelayed(300ms)` 再 stop；
   Dart 侧拿到 false 也隔 300ms 再调一次（双保险，失败的代价是把用户关在 App 里）；
5. `FocusLockChannel.dispose()` 兜底：Activity 销毁若还锁着，直接 `stopLockTask()`。

**门禁**：`analyze` 零 issue；`test` `+487`（新增 1 条：mock 通道让 `enterLockTask` 回 2，
断言暂停时必须调 `exitLockTask`，并断言页面销毁时再调一次）；
`build apk --release` 通过（这一步才验得到 Kotlin）。
