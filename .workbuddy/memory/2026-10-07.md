### 先画流程图 + 界面示意，用户拍板四件事

1. **锁定强度**：两档都做 —— 默认沉浸式全屏（不需任何系统设置），设置里可开「更强锁定」
   调用系统「屏幕固定」（`startLockTask`）。理由：真 kiosk 要 device owner，得用 adb 把手机
   设成受管设备，普通用户做不到；而屏幕固定要用户在系统设置里先打开，不少国产 ROM 还阉割。
2. **命名**：三级分类 + 自定义，并**入库**（故有 v9 迁移）。
3. **反馈**：震动 + 声音。
4. **休息**：不锁屏。

### 摸现状时发现三个真 bug（旧 `focus_timer_page.dart`）

1. **计时快 5 倍**：`AppConstants.focusTicker` 是 200ms，回调却每次 `_remainingSeconds -= 1`
   —— 每 200 毫秒扣 1 秒，25 分钟的专注 5 分钟就"完成"。
   **根因不是间隔取错，而是"拿累加器表示剩余时间"这条路本身错**：定时器抖动、掉帧、被系统
   延后都会永久沉淀成误差，且刷新间隔与步长一旦不一致就整体跑偏。
2. **`started_at` 记的是结束时刻**：`_finish()` 里用 `DateTime.now()` 当开始时间写库。
   统计页按 `started_at` 落在哪一周汇总「本周专注次数」，跨零点的那一节会整段算进第二天。
3. **中途放弃完全不留痕**：只有 `_finish()` 写库，而需求恰恰要"退出时告诉他已坚持多久"。

好消息：统计页 `teaching_insight_service.dart` **只汇总 `completed` 为真的记录**，
所以放弃的记录进库不会污染「本周专注次数 / 累计分钟」。

### 重启后仍失败 —— 旧结论「重启即可恢复」被推翻

用户重启后（用 `GetTickCount64()` 查 uptime = **1.3 分钟**，确认是真重启），
`flutter --version` 照样崩 `CreateFile failed 231`。于是做了一轮系统排查：

把范围钉死在一个**最小可复现探针**上（`%TEMP%\wb_spawn_probe.dart`）——
它证明 **Dart VM 连 `cmd.exe /c ver` 都 spawn 不了**，三种调用方式
（`Process.runSync` 继承 stdio / `runSync` 捕获输出 / `Process.start`）全挂，连发 20 个成功 0 个。

**关键对照**：Python 的 `subprocess` 起同样的 `cmd /c ver` **完全正常**；
`dart-sdk\bin\dart.exe --version` **也正常**。坏的只有「Dart VM 建命名管道去 spawn 子进程」这一条路径。

已逐项排除（详见 `MEMORY-DETAIL.md` 新增的「工具链故障」一节）：

| 假设 | 结论 |
| --- | --- |
| 重启一下就好 | ❌ 重启后（uptime 1.3 分钟）照样失败 |
| 沙箱在拦 | ❌ 加 `dangerouslyDisableSandbox` 一样 |
| WorkBuddy 注入的环境变量 | ❌ 最小环境（只留 SystemRoot/PATH/TEMP/PATHEXT）一样 |
| 被塞进 Job 对象 | ❌ 读出来只有 `BREAKAWAY_OK`，无 `ActiveProcessLimit`、无 UI 限制 |
| conhost / 控制台归属 | ❌ `CREATE_NEW_CONSOLE` 一样 |
| 命名管道本身坏了、或名字冲突 | ❌ Python 用 ctypes 直接调 `CreateNamedPipeW`+`CreateFileW` 四种组合全 OK；管道命名空间 133 条里 **dart/flutter 相关 0 条** |

`CREATE_BREAKAWAY_FROM_JOB` 想验证「脱离 WorkBuddy 进程树是否就好」，被拒 `WinError 5`，做不了。

**定论（用户在自己 cmd 窗口里跑同一条探针）**：`[runSync cmd] exit=0`、`[Process.start] exit=0`、
**`[连发 20 个] 成功 20 个`** —— 全绿。同一份 `dart.exe`、同一条命令，在 WorkBuddy 的
Bash / PowerShell 工具里 100% 失败。

> **所以不是机器坏了，是 WorkBuddy 的进程环境（Sandbox Center 那一层）让 Dart VM 建不出命名管道。**
> 环境变量、Job、控制台归属、沙箱开关、管道本身全部排除；换一个**不由 WorkBuddy 启动的终端**就好了。

**处置**：写了一键脚本 `%TEMP%\release_v1.0.8.bat`（先 `flutter --version` 自检，再
`tool\release.py --no-bump --push`），请用户在自己的终端里双击运行。

### 第二次中断：我给的 .bat 把发布整个静默跳过了（我的锅）

用户跑第一版脚本，输出只有：

```
 step 0/1  sanity check: flutter / dart spawn
Flutter 3.41.6 • channel stable • ...
```

然后回到提示符 —— **发布那一步一个字都没输出**。查仓库：`HEAD` / 标签 / `dist/releases` 全是原样，
确认真的没执行。

**根因**：脚本里在 `flutter --version` 之后写了 `if errorlevel 1 (... exit /b 1)` 当门禁，
而 **`flutter.BAT` 成功时也返回非 0 退出码** → 自检被误判成失败 → 直接退出。
而我第一版脚本里那一行还是 `flutter --version`（没 `call`），在 `.bat` 里也不会返回，
判断更不可信。

**规矩（已写进红线）**：给 flutter 做 `.bat` 包装时，自检**只展示不判定**；
要判定只用自己的退出码，并在末尾一次性报告，中途不要 `exit /b`。
第二版脚本已去掉该门禁，并且加了两条更可靠的守卫（`cd` 后核对 `%CD%`、`python.exe` 存在性）。

**代价**：用户白等一次。以后凡是交给用户双击运行的东西，**先在本地把"每一条分支"过一遍**，
尤其是"看起来跑完了但实际一步没跑"这种情况 —— 它比报错更难被发现。

**教训**：`MEMORY.md` 里原本写死「杀进程无效、**只能重启电脑**」，这条今天被证伪了 ——
一条**没有任何实验约束**的结论写进红线，会在真出事时把人带偏。以后这类"现象→解法"的对应，
要么写清**判据**，要么标注**未穷尽**。
