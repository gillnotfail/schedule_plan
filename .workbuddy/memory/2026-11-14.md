
## 第 36 轮：学生/班级信息改了，考勤页名单要实时（v1.0.15）

**用户报告**：*"如果教师在开头导入学生名单后，如果修改部分学生信息，对应到课表页-去点名-跳转考勤页，
这个学生信息是没有修改的……常见的修改包括但不限于：修改部分学生姓名、班级、性别等信息；删除、新增学生等。"*

**查到的事实**（写下来免得下次重查）：
- 考勤名单走 `StudentRepository.listByClasses`，**每次都是实时查库**；`_loadStudents` 在
  「去点名」「切日期」「换课」「切回 Tab」四条路上都会被调用 —— 所以**姓名/学号/增删本身是会刷新的**，
  widget 测试已锁死（`test/widget/attendance_roster_refresh_test.dart` 4 条）。
- **真正复现出来的 bug**：`_refreshHolidayContext`（切 Tab 回来那条路）**没有 `_loadClasses()`**，
  而 `_classNames`/`_classOrder` 只在 `initState` 读一次 → **改班名永远不生效、新建的班连名字都没有**
  （分组横带回落成「班级管理」）。去掉 `_loadClasses()` 能让 `班级改名后…` 那条用例稳定失败，加回来通过。
- 顺带修：首次 `_loadAll` 与「去点名」撞车时，先发起的那次后返回会覆盖/清空名单（加 `_lessonToken`/
  `_studentToken` 世代号丢弃旧返回）。
- `AttendancePage` 加可注入 `HolidayService`：不注入时默认实例走 `SettingsRepository()` →
  `AppDatabase.instance()`，widget 测试里会把 pump 挂住（上一版测试卡 8 分钟就是这么来的）。

**测试**：`test/widget/attendance_roster_refresh_test.dart` 5 条（去点名改名/改学号/转班、新增/删除、
切 Tab 回来、班级改名、首屏未加载完就点去点名）。全量 **548 全绿**，analyze 零 issue。

## 第 37 轮：检查更新报「版本信息暂时取不到」——真因是 Gitee raw 回 451（v1.0.16）

**用户报告**：*"检查更新时显示版本信息暂时找不到，清单不可用。是什么原因，推送的时候清单不对吗"* ——
**推送没问题**，逐字段核对过：两仓库 `updates/latest.json` 各 39697 字节、内容一致、
`schemaVersion=1`、16 条 releases、`assets` 的 size 与 64 位 sha256 齐、`deltas` 的 baseSha256 齐、
仓库都是 public、`default_branch=main`。

**实测真因（决定性证据）**：
```
curl https://gitee.com/jeo-xie/schedule_plan/raw/main/updates/latest.json        -> HTTP 451
curl https://gitee.com/api/v5/repos/jeo-xie/schedule_plan/contents/updates/latest.json?ref=main
                                                                               -> HTTP 200, 56748 B
```
**Gitee 的 raw 会对密集请求回 451（Unavailable For Legal Reasons，风控）**，而客户端当时的三条源是
raw(451) → GitHub raw(国内不通) → jsDelivr(国内常不通)，于是全灭。另外 Gitee raw 现在会 302 到
`raw.giteeusercontent.com`，**本机 curl/python/Dart 对那个子域全部 TLS 握手失败，而 gitee.com 正域正常** ——
只放行正域的网络里 raw 必死。

**改法**（`lib/data/services/update_service.dart`）：
1. 源从 3 条扩到 **7 条并改成并发**（`Future.wait` + Completer，谁先回用谁）：
   Gitee raw 带 `?t=` → **Gitee 内容 API**（绕开 raw 子域，200 不跳转，是真保命源）→ raw 不带参（绕 451）
   → GitHub raw → jsDelivr 的 cdn/fastly/gcore 三个域名。清单请求超时单独压到 `manifestTimeout=8s`。
2. 新增 `parseManifestBody`：内容 API 会包一层 `{"encoding":"base64","content":"..."}`，
   base64 按 60 字符换行，解码前要剥空白。
3. **失败分两类报**：`reachedServer` 为假 → `UpdateFailure.network`（没连上服务器）；
   为真 → `UpdateFailure.manifest`（连上了内容不认）。以前一律报后者，等于把网络问题说成清单问题。
   `failureDetail` 现在列每条源的结论（`gitee 451 · gitee-api 超时 · github 握手失败`，最多 4 条 + "另 N 条"）。
4. **只有拿到清单才记 `lastCheckAt`**，失败不再吃掉一天的自动检查机会。

**教训**：诊断「清单不可用」时先区分**传输层**和**内容层**。手工核验 Gitee raw 一定要看 `%{http_code}`
而不是"打不开/打不开就行"；451 是限流不是内容错。本机 `raw.githubusercontent.com` / `cdn.jsdelivr.net`
/ `raw.giteeusercontent.com` 全部 TLS 失败，**本机连不上不代表手机连不上**，别据此剔源。

**门禁**：analyze 零 issue；test **556 全绿**（+8，`test/unit/update_source_test.dart` 重写为 13 条：
源顺序 7 条、镜像只往后加、base64 包装、折行解码、坏内容返回 null、诊断摘要截断、异常压字）。
**发布** `1.0.16+17`，`16e06b6` 功能 → 发布脚本自提交；四附件 + 两源匿名抽查通过。

之后才能用应用内更新。
