## 第 19 轮（续）：发 v1.0.4 时挖到的 jsDelivr purge 两个坑

发 v1.0.4（tag `v1.0.4` → `a337a20`，4 个附件；分差复用 59.5% / 51.0%，下载量仅整包的 16.46% / 19.87%），
发布脚本报「jsDelivr 返回异常」，但输出里分明是 `"status": "finished"` —— 挖下去是两个问题：

1. **`status == "finished"` 不等于清成功**。真正要读的是
   `paths["/<owner>/<repo>@main/updates/latest.json"].throttled`。被限流时返回
   `{"status":"finished", "throttled":true, "throttlingReset":406}` —— **状态是"完成"，但这个路径根本没清**。
   只看 `status` 会把"没清掉"误判成"已清理"，然后手机上继续看到旧版本。
   限流窗口实测约 6 分钟，**连续发两个版本必中**（v1.0.3 刚清过，v1.0.4 就被打回）。
2. **purge 端点必须用 curl 调**。本机 Python `urllib` 访问 `purge.jsdelivr.net` 一律
   `WinError 10054`（远程强制断开）；**强制直连（`ProxyHandler({})`）也一样**，所以不是代理问题。
   同一个地址 curl 稳定 200。而 `api.github.com` 的 urllib 请求完全正常 —— 所以只有这一条会挂，
   别扩大化成"网络全废"。对照实验：`release.py` 里 GitHub 上传成功、purge 失败，正是这个组合。

`tool/release.py` 的修法：
- `_request_purge()`：**curl 优先**（`shutil.which("curl")`，走 `capture_output`），找不到 curl 才回落 urllib。
- `purge_cdn_cache(max_wait_seconds=600)`：判定改成 `finished && not throttled` 才算成功；
  被限流且剩余时间在上限内 → 打印剩余秒数、`time.sleep(reset + 2)` 后**自动重试一轮**；
  超时才告警并打出 `throttlingReset` 与手工补清命令。
- 实测有效：输出 `jsDelivr 限流中，等 355 秒后重试…` → `jsDelivr 清单缓存已清理`，
  随后 `@main` 与本地 `updates/latest.json` **逐字节一致**（sha256 `6d60689d34bd7029`，1.0.4+5）。

`docs/RELEASE.md` §4 与排障表补上"看 `throttled` 不要只看 `status`"「清完回读 sha256 复核」。

## 顺带记录的诊断技巧
- Git Bash 里调 Windows 原生命令，`/FO` 这种参数会被 MSYS 改写成路径（`C:/Users/.../FO`）；
  要用 `//FO` 双斜杠。
- `tasklist` 输出是 GBK，Python 里 `sys.stdin.buffer.read().decode('gbk', errors='replace')` 才不炸。
- PowerShell 工具在本机管道紧张时**会静默吞掉 stdout**（只回 "Command completed with exit code 0"），
  出现这种"命令成功但没输出"就先去想管道问题。
