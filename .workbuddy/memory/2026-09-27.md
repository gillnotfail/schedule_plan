## token 两次都到不了手（本轮真正的卡点）

用户先后给了两个新生成的细粒度 PAT，收到的长度**都是 31 个字符**。

（这两个 token 的**字面内容已从本文移除**：它们是已失效的截断串，但仓库一旦转公开，
任何半截凭据都不该留在历史里。要复现这个现象，看下面的长度与形态描述就够。）

`od -c` 逐个字符看过：**没有隐藏字符、没有尾随空白**，形态就是
`github_pat_`（11）+ 20 个随机字符，**连第二个下划线都没有**。而真实形态是
`github_pat_<22位>_<59位>`、共 **93** 字符。

两个独立生成的 token 落在同一个长度上，只能说明是**复制／粘贴链路在截断**，
不是在 GitHub 侧生成的 token 有问题。而且第二次 token 在消息**开头**
（后面还跟着文字）也照样断在 31，说明与消息位置无关。

两次都是服务端一句 `401 Bad credentials`——这个报错**极易被误判成「权限不够」**，
让人去反复重新生成 token 而永远修不好。

结论与做法：
- 让用户**用编辑器直接写** `~/.schedule_plan-release.env`，彻底绕开聊天链路。
  该文件已预置好格式（只差等号右边的值），路径 `C:\Users\jeo\.schedule_plan-release.env`。
- 新增 `token_file_status()`：区分「文件不存在 / 文件里没有 `GITHUB_TOKEN=` 那一行 /
  等号右边是空的 / 有值但读不出来」。原先四种都只说「没有可用的 GITHUB_TOKEN」，
  而用户明明看到文件在那儿，只会怀疑脚本读错了路径。

## 发布结果

  两个附件都传上去了。

  这条比"size 对得上"强得多，也省得把 45 MB 再拉回来。

## 踩到的真缺陷：release.py 的顺序反了（已修）

第一次真跑时出现两个互相关联的症状：

1. `git push` 标签被拒：`! [rejected] v1.0.0 -> v1.0.0 (already exists)`
2. 远端标签 `v1.0.0` 指向 `f4ec277`（发布**之前**的提交），而不是发布提交 `2ffe4c2`

根因：脚本原先**先建 Release、后提交打标签推送**。GitHub 收到创建 Release 的
请求时，如果远端还没有这个标签，会照着 `target_commitish`（默认仓库默认分支的
HEAD）**自己造一个同名标签**。于是：

- Release 挂在不含本次发布的旧提交上；
- 随后真正 `git push` 标签又被 `already exists` 拒绝。

**两个症状都在"上传成功"之后才出现**，日志看起来一切正常，很容易被误判成权限问题。

修法（三层）：
- 主流程**倒过来**：先 `commit_and_tag` → 再 `upload_release`；
- `upload_release` 显式传 `target_commitish = <本次提交 SHA>`，不给它机会自己猜；
- `commit_and_tag` 推送后**再 `ls-remote` 复核一次**远端标签存在（`git push` 成功
  但标签指向别处这种事，只能自己验）；
- 参数层直接拦：**要建 Release 就必须去掉 `--no-commit` 且带上 `--push`**，
  否则 `die` 并说明理由。

已踩到的那次靠 `git push origin +refs/tags/v1.0.0:refs/tags/v1.0.0`
把标签硬挪到正确提交（`053a04f` → 提交 `2ffe4c2`）。

## 最大的发现：仓库是 private，应用内升级必然失败

`GET /repos/gillnotfail/schedule_plan`：**匿名 404 / 带 token 200** → 私有。
jsDelivr 对私有仓库直接 **404**（`Couldn't find the requested file ... in
gillnotfail/schedule_plan`）。

**应用里没有、也不该有凭据**，它只能匿名取清单和安装包。所以私有仓库下：
发布流程全绿，而手机端**永远看不到更新**，一个报错都没有。

两个地址都受影响：清单（raw / jsDelivr）和安装包（`github.com/.../releases/download/...`）。

已写进 `docs/RELEASE.md` §2.1（排在首次配置第一条）和 `README.md` 的发布一节，
并给出匿名探测的判断命令。**不要**把 token 塞进 App 换取私有仓库——APK 可反编译。

## 本机网络补充

- `raw.githubusercontent.com` **本机完全不可达**（对 `flutter/flutter` 这种公开仓库
  也是 `http=000`），所以**在这台机器上验证不了应用内取清单的那条路**——
  这是网络问题，不是仓库配置问题。jsDelivr 可达（公开仓库 200 / 私有仓库 404）。
- 顺带发现命令有时会显示 `Sandbox bypassed (escalation-approved)`：
  **后台任务没有升级权限时读不到 `~/.ssh/known_hosts`**（`hostkeys_foreach failed:
  Permission denied` → `Host key verification failed`），于是那次推送失败。
  前台跑同样的命令就正常。以后要在后台跑需要 ssh 的脚本，得留意这一点。
